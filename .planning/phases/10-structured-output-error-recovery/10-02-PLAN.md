<objective>
Implement partial-success pipeline execution and enhanced per-step status display.

When a delivery step (Notion, Slack, Webhook, Save) fails, the pipeline engine continues executing subsequent independent steps instead of halting. Processing step (LLM) failures still halt execution because downstream steps depend on their output. The frontend displays per-step status with clear visual indicators for succeeded, failed, and skipped steps.

Purpose: Prevent one broken delivery from blocking all other deliveries in the same pipeline. Give users clear visibility into which steps worked and which did not.

Output: Modified pipeline_engine.rs (partial-success logic), pipelines.rs (step status model), main.js (per-step status UI).
</objective>

<task type="auto">
  <name>Task 1: Implement partial-success pipeline execution for delivery step failures</name>
  <files>src-tauri/src/pipeline_engine.rs, src-tauri/src/pipelines.rs</files>
  <action>
**In pipelines.rs:**

1. Add a helper function (or implement on ConnectorType) to classify step types:
   ```rust
   impl ConnectorType {
       /// Delivery connectors send output to external services.
       /// Their failure should not block other independent steps.
       pub fn is_delivery(&self) -> bool {
           matches!(self, ConnectorType::Notion | ConnectorType::Slack | ConnectorType::Webhook | ConnectorType::Save)
       }
   }
   ```

   Note: LLM is a "processing" connector (produces output consumed by downstream steps). Mcp is also processing (when implemented).

**In pipeline_engine.rs:**

2. Modify `execute_pipeline_internal()` to implement partial-success logic. Replace the current "fail and stop" behavior with:

   a. Before the step loop, create a `Vec<StepOutcome>` to track results:
      ```rust
      struct StepOutcome {
          step_index: usize,
          step_name: String,
          connector: ConnectorType,
          result: Result<PathBuf, String>,
      }
      let mut outcomes: Vec<StepOutcome> = Vec::new();
      let mut has_failure = false;
      ```

   b. In the step loop, after a step completes (Ok or Err):
      - **On Ok:** Record outcome, emit "done" event, continue as before.
      - **On Err for a PROCESSING step (LLM, Mcp):** Record outcome, emit "failed" event, mark `has_failure = true`. Then mark ALL remaining steps as "skipped" (they depend on this step's output). Break out of the loop.
      - **On Err for a DELIVERY step (Notion, Slack, Webhook, Save):** Record outcome, emit "failed" event, mark `has_failure = true`. **Continue to the next step** (do NOT break). However, check if the next step's `input` references the failed step's name -- if so, that step must be skipped (its input won't exist).

   c. For skipped steps: Write a step .md file with `status: skipped` and a note: "Skipped because step '{dependency}' failed". Emit a progress event with status "skipped".

   d. After the loop, determine final pipeline status:
      - If `has_failure` is false: `PipelineStatus::Done`
      - If `has_failure` is true: `PipelineStatus::Partial`
      - Store the error from the FIRST failed step in the pipeline state (for backward compatibility with the existing UI that shows the first error)

3. Add "skipped" to the `PipelineProgressPayload` status values (it already accepts arbitrary strings).

4. Ensure the `get_step_outputs` command correctly reads "skipped" status from frontmatter -- it already uses `parse_step_status()` which reads the `status:` field generically, so "skipped" will work automatically.

5. Important edge cases:
   - A pipeline with steps [LLM-A, Notion-B, Slack-C] where LLM-A fails: both Notion-B and Slack-C are skipped (they depend transitively on LLM-A's output).
   - A pipeline with steps [LLM-A, Notion-B, Slack-C] where Notion-B fails: Slack-C still executes (if its input is LLM-A, not Notion-B). If Slack-C's input IS Notion-B, then Slack-C is skipped.
   - A pipeline with steps [LLM-A, Notion-B, LLM-C, Slack-D] where Notion-B fails: LLM-C executes (its input is likely "transcript" or LLM-A, not Notion-B), Slack-D executes.
   - Input resolution: Check each step's `input` field. If `input == "transcript"`, the step is independent of any previous step failure. If `input == <some_step_name>`, check if that step failed or was skipped.

6. To determine if a step should be skipped: maintain a `HashSet<String>` of failed/skipped step names. Before executing each step, check if `step.input` is in the failed set (unless input is "transcript"). If so, skip the step.
  </action>
  <verify>
`cargo check` (or structural verification). Trace these scenarios mentally:

- [LLM, Notion, Slack(input=Notion)] with Notion failure -> Slack skipped -> Partial
- [LLM-fail, Notion, Slack] -> all skipped -> Partial
- [LLM, Notion, Slack] all succeed -> Done

     - Done: green checkmark icon (Unicode or CSS class) + step name
     - Failed: red X icon + step name + error message (expandable or inline)
     - Skipped: gray circle icon + step name + "(skipped)"
     - Pending: empty circle icon + step name (shouldn't normally appear in final state)
   - Only show the step list for `partial` status (not `done` -- `done` means all succeeded, no need for detail)
