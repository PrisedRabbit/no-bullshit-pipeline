<objective>
Implement JSON retry logic for structured delivery steps and preserve raw AI output on failure.

When a Notion delivery step receives invalid JSON from the AI, the pipeline engine detects the JSON parse failure, builds a corrective prompt containing the failed output, re-invokes the LLM once with a stricter instruction, and only then reports failure if the retry also fails. On final failure, the step output file preserves the raw AI response alongside an actionable error message.

Purpose: Prevent single LLM formatting mistakes from causing silent pipeline failures. Give users visibility into what the AI actually returned so they can diagnose prompt issues.

Output: Modified notion.rs (error categorization + raw output preservation), pipeline_engine.rs (retry orchestration), llm.rs (retry execution function).
</objective>

  <name>Task 1: Categorize Notion connector errors and preserve raw output on failure</name>
  <files>src-tauri/src/connectors/notion.rs</files>
  <action>
1. Create a public enum `NotionErrorKind` with two variants:
   - `JsonParse { message: String, raw_output: String }` -- JSON extraction or validation failed
   - `Other(String)` -- API errors, config errors, etc.

2. Create a public struct `NotionError` with fields:
   - `kind: NotionErrorKind`
   - Implement `Display` for `NotionError` (delegates to inner message)
   - Implement `From<NotionError> for String` so existing `Result<PathBuf, String>` callers still work

3. Modify `extract_json_array()` to return `Result<Vec<serde_json::Value>, NotionError>` instead of `Result<..., String>`:
   - All error returns become `NotionError { kind: NotionErrorKind::JsonParse { message: <existing error text>, raw_output: <full body text (not truncated to 500 chars)> } }`
   - Keep the 500-char preview in the `message` for display, but store the full body in `raw_output`

4. Modify `validate_llm_output_for_notion()` to return `Result<(), NotionError>`:
   - Same pattern: wrap errors as `NotionErrorKind::JsonParse` with full raw_output

5. Modify the `execute()` function:
   - Change internal error handling so `extract_json_array` and `validate_llm_output_for_notion` errors are caught
   - On `JsonParse` error: return `Err(NotionError)` with kind `JsonParse` (pipeline engine will handle retry)
   - On final failure (after retry, which pipeline engine orchestrates): write the step .md file with `status: failed`, the error message, AND the raw AI output in the body section below the frontmatter (format: `## Error\n{error_message}\n\n## Raw AI Output\n{raw_output}`)
   - API errors and config errors remain `NotionErrorKind::Other`

6. Add a public helper function `execute_with_raw_preservation()` that:
   - Takes the same args as `execute()` plus an optional `raw_llm_output: Option<&str>`
   - When `raw_llm_output` is `Some`, on ANY failure writes the step .md with the raw output preserved
   - This is used by the pipeline engine after retry fails, to ensure raw output is always captured

Note: The `execute()` function's return type remains `Result<PathBuf, String>` for backward compatibility with the pipeline engine. The `NotionError` type is used internally and exposed via a new `execute_structured()` function that returns `Result<PathBuf, NotionError>`, which the pipeline engine calls instead of `execute()`.

<task type="auto">
  <name>Task 2: Add LLM retry function and pipeline engine retry orchestration</name>
  <files>src-tauri/src/connectors/llm.rs, src-tauri/src/pipeline_engine.rs</files>
  <action>
**In llm.rs:**

1. Add a public async function `execute_retry()` with signature:
   ```rust
   pub async fn execute_retry(
       failed_output: &str,
       original_prompt: &str,
       config: &serde_json::Value,
       output_dir: &Path,
       step_name: &str,
       step_input: &str,
       step_description: Option<&str>,
   ) -> Result<PathBuf, String>
   ```

2. This function builds a corrective prompt:
   ```
   The previous AI response was not valid JSON. Here is what was returned:

   ---BEGIN FAILED OUTPUT---
   {failed_output (first 2000 chars)}
   ---END FAILED OUTPUT---

   Fix this output to be a valid JSON array. Rules:
   1. Return ONLY a JSON array: [{...}, ...]
   2. No markdown, no code fences, no prose before or after
   3. No trailing commas
   4. All strings must be properly quoted
   5. Preserve the original data as closely as possible

   Original instruction (for context):
   {original_prompt (last 500 chars -- the format spec portion)}
   ```

3. The function uses the same provider/model from `config` (reuses `LlmConfig::from_value`), calls the same cloud_ai functions, and writes the output .md with a note in description: "Retry attempt for JSON correction".

**In pipeline_engine.rs:**

4. Modify the Notion step dispatch in `execute_pipeline_internal()`:
   - Instead of calling `connectors::notion::execute()`, call a new function `connectors::notion::execute_structured()` which returns `Result<PathBuf, NotionError>`
   - If the result is `Err(NotionError { kind: JsonParse { raw_output, .. }, .. })`:
     a. Log: "Notion JSON parse failure on step '{}', retrying with corrective prompt"
     b. Read the LLM step output from the previous step's .md file (the step that fed into this Notion step -- its path is `output_dir.join(format!("{}.md", step.input))`)
     c. Call `connectors::llm::execute_retry()` with the `raw_output` as `failed_output` and the LLM output file content as context
     d. If retry LLM call succeeds: re-attempt `connectors::notion::execute_structured()` with the retry output path as input
     e. If retry also fails (either LLM error or second Notion parse error): write the step .md with raw output preserved (use the `raw_output` from whichever attempt failed last), then fall through to the existing error handling path
   - If the result is `Err(NotionError { kind: Other(..), .. })`: no retry, fall through to existing error handling
   - Max 1 retry total (the code path does not loop)

5. To get the augmented prompt for the retry context, store the `augmented` prompt string (from the N+1 look-ahead block) in a variable that persists through the Notion step execution, so it can be passed to `execute_retry()`.

6. Important: The retry only applies to Notion steps (structured delivery). Other connector failures continue to behave exactly as before (no retry).
  </action>
