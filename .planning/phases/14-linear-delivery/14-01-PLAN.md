Create `src-tauri/src/connectors/linear.rs` following the Notion connector pattern (`connectors/notion.rs`). This is the bulk of the work. Specific components:

**1. Error types** (mirror NotionErrorKind/NotionError exactly):
- `LinearErrorKind::JsonParse { message: String, raw_output: String }` — for JSON extraction and structural validation failures (retryable)
- `LinearErrorKind::Other(String)` — for API errors, config errors, auth failures (non-retryable)
- `LinearError { kind: LinearErrorKind }` with `Display` and `From<LinearError> for String` impls

**2. Config struct:**
- `LinearConnectorConfig { integration_id: String }` parsed from `config.get("integration_id")` (same pattern as NotionConnectorConfig)

**3. JSON extraction — `extract_json_object()`** (NOT `extract_json_array` — Linear creates ONE issue):
- Strip YAML frontmatter via `crate::connectors::strip_frontmatter()`
- Try direct parse as `serde_json::Value` (must be an object, not array)
- Try extracting from ` ```json ... ``` ` code fence
- Try extracting from ` ``` ... ``` ` bare code fence
- On failure: return `LinearErrorKind::JsonParse` with full raw body in `raw_output`, 500-char preview in `message`

**4. Validation — `validate_llm_output_for_linear()`:**
- Input: parsed JSON object, profile, raw_output string
- Check the object has at least one key matching a known Linear field: "title", "description", "priority", "status", "labels", "assignee"
- On structural mismatch: return `LinearErrorKind::JsonParse` (so it gets retried)

**5. Field resolution functions (case-insensitive matching against profile data):**

- `resolve_status(value: &str, profile: &LinearIntegrationProfile) -> Option<String>`:
  LLM provides status name (e.g. "In Progress") -> case-insensitive match against `profile.workflow_states[].name` -> return the matching `id`. Return `None` if no match.

- `resolve_priority(value: &serde_json::Value, profile: &LinearIntegrationProfile) -> Option<i32>`:
  LLM provides priority as string label (e.g. "High") or number (2). If string, case-insensitive match against `profile.priorities[].label` -> return `.priority`. If number, validate 0-4 range -> return as i32. Return `None` if no match.

- `resolve_labels(value: &serde_json::Value, profile: &LinearIntegrationProfile) -> Vec<String>`:
  LLM provides array of label name strings (e.g. ["Bug", "Frontend"]) or single string. For each, case-insensitive match against `profile.labels[].name` -> collect matched `.id` values. Skip unmatched labels silently.

- `resolve_assignee(value: &str, profile: &LinearIntegrationProfile) -> Option<String>`:
  LLM provides member name. Case-insensitive match against `profile.members[].name` OR `profile.members[].display_name` -> return matching `.id`. Return `None` if no match.

**6. GraphQL mutation builder — `build_issue_input()`:**
- Input: parsed JSON object, profile
- Returns: `serde_json::Value` representing the `IssueCreateInput` GraphQL variable
- Always include: `teamId` (from `profile.team_id`), `title` (required, from JSON "title" field)
- Conditionally include (only if LLM provided and resolution succeeded):
  - `description`: string from JSON "description"
  - `stateId`: resolved from "status" via `resolve_status()`
  - `priority`: resolved from "priority" via `resolve_priority()`
  - `labelIds`: resolved from "labels" via `resolve_labels()` (only if non-empty)
  - `assigneeId`: resolved from "assignee" via `resolve_assignee()`
- If no title found: return `LinearError` with `Other` kind

**7. GraphQL mutation execution — `create_issue()`:**
- Async function taking token and the input variables
- Uses `reqwest::Client` directly (same pattern as `graphql_request` in `integrations/linear.rs` — but import/call the helper or duplicate minimally)
- Mutation: `mutation IssueCreate($input: IssueCreateInput!) { issueCreate(input: $input) { success issue { id identifier title url } } }`
- On success: extract and return `{ id, identifier, title, url }` as a struct or tuple
- On failure: return `LinearError` with `Other` kind including the API error message

IMPORTANT: The `graphql_request` helper is in `integrations::linear` as a private function. Rather than making it pub, create a minimal `linear_graphql_request()` in the connector that takes token + query + variables and returns Result. OR make the `graphql_request` in `integrations/linear.rs` pub(crate) so both modules can use it. The pub(crate) approach is cleaner — change `async fn graphql_request` to `pub(crate) async fn graphql_request` in `integrations/linear.rs`.

**8. Output file helpers** (mirror Notion pattern):
- `write_success_output()`: YAML frontmatter with `connector: linear`, `status: done`, `issue_id`, `issue_identifier`, `issue_url`
- `write_failure_output()`: YAML frontmatter with `connector: linear`, `status: failed`, `error`, optional raw LLM output body

**9. Execute entry points** (three functions, mirroring Notion exactly):
- `execute()` -> `Result<PathBuf, String>` — standard signature for non-retry callers
- `execute_structured()` -> `Result<PathBuf, LinearError>` — for pipeline engine retry detection
- `execute_with_raw_preservation()` -> `Result<PathBuf, String>` — final-failure write path with raw output preserved

All three call a shared `execute_inner()` that: parses config, loads profile via `load_linear_profile()`, gets token via `get_linear_token()`, reads input file, extracts JSON object, validates, builds issue input, creates issue via GraphQL, writes success output.

**B. `src-tauri/src/pipeline_engine.rs` — Add Linear match arm with retry:**

Add a `ConnectorType::Linear` match arm in the main step execution `match step.connector` block (after the Notion arm, before Mcp). This arm follows the EXACT same retry pattern as the Notion arm (lines 516-639), with these differences:

1. Use `connectors::linear::LinearErrorKind` instead of `NotionErrorKind`
2. Call `connectors::linear::execute_structured()` instead of `connectors::notion::execute_structured()`
3. Call `connectors::linear::execute_with_raw_preservation()` instead of Notion's
4. In the `build_augmented_prompt` call, pass the Linear `integration_id` to the same function — BUT NOTE: `build_augmented_prompt` currently only supports Notion profiles. For now, pass empty string for the integration_id parameter (prompt augmentation is Phase 15's job). The retry only needs the LLM step's config for provider/model, not the augmented prompt content.
   Actually, looking more carefully: the `original_prompt` is used in `execute_retry` as context for the corrective prompt (last 500 chars). For Linear retry, the corrective prompt just needs the failed output. So pass `""` as original_prompt or build a minimal one from the LLM step config directly. The simplest approach: call `build_augmented_prompt` with empty integration_id — it will fail (Notion profile not found) so catch that and fall back to reading the LLM step's prompt directly from config. Better approach: extract the base prompt from the LLM step config without augmentation:
   - Read `prompt_template` or `prompt_inline` from `llm_step.config`
   - Read the input file content
   - Substitute variables
   - Pass that as `original_prompt` to `execute_retry`

   Use this pattern:
   ```rust
   let original_prompt = {
       let llm_input_path = resolve_input_path(recording_id, pipeline_name, &llm_step.input);
       let raw_input = std::fs::read_to_string(&llm_input_path).unwrap_or_default();
       let input_content = crate::connectors::strip_frontmatter(&raw_input);
       if let Some(tmpl) = llm_step.config.get("prompt_template").and_then(|v| v.as_str()).filter(|s| !s.trim().is_empty()) {
           crate::prompt_templates::get_prompt_template_internal(tmpl)
               .map(|t| crate::prompt_templates::substitute_variables(&t.prompt, input_content))
               .unwrap_or_default()
       } else if let Some(inline) = llm_step.config.get("prompt_inline").and_then(|v| v.as_str()).filter(|s| !s.trim().is_empty()) {
           crate::prompt_templates::substitute_variables(inline, input_content)
       } else {
           String::new()
       }
   };
   ```
